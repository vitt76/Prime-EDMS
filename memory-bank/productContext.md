# Product Context: Prime-EDMS

## Контекст продукта

**Prime-EDMS** — это enterprise-level система управления цифровыми активами (Digital Asset Management, DAM) и данными, построенная на базе Enterprise Document Management System (EDMS) Mayan EDMS. Система была существенно переработана и улучшена для соответствия современным трендам DAM-систем с фокусом на AI-обработку, аналитику использования и эффективное распределение контента.

## Почему существует этот проект

### Проблемы, которые решает система

#### 1. Фрагментированное хранение медиа-контента
**Проблема:** Медиа-файлы разбросаны по разным системам, локальным дискам, облачным хранилищам без единой точки доступа.

**Решение:**
- Централизованное хранилище с поддержкой локального и облачного (S3) бэкендов
- Импорт из внешних источников (Яндекс.Диск)
- Единый каталог всех активов с метаданными

#### 2. Ручное тегирование и категоризация
**Проблема:** Ручное добавление тегов и метаданных к тысячам файлов — трудоемкий и непоследовательный процесс.

**Решение:**
- Автоматическое AI-обогащение метаданных через множественные провайдеры (YandexGPT, GigaChat, OpenAI, Claude, Gemini, Qwen Local, KieAI)
- Извлечение описаний, тегов, категорий, людей, локаций, доминирующих цветов
- Настраиваемые пресеты метаданных для разных типов контента

#### 3. Длительный поиск нужных активов
**Проблема:** Пользователи тратят много времени на поиск нужных медиа-файлов из-за отсутствия эффективного поиска.

**Решение:**
- Полнотекстовый поиск с поддержкой JSON-полей через GIN индексы PostgreSQL
- Поиск по AI-тегам, описаниям, категориям, метаданным
- Фильтрация по типу файла, дате, владельцу, статусу workflow
- Целевой KPI: сокращение времени поиска с 30 минут до 5 минут

#### 4. Отсутствие контроля версий и истории изменений
**Проблема:** Невозможность отследить историю изменений файлов, вернуться к предыдущим версиям, понять кто и когда вносил изменения.

**Решение:**
- Версионирование документов через систему DocumentFile/DocumentVersion
- История изменений с привязкой к пользователям
- Неразрушающее редактирование (каждое сохранение создает новую версию)
- Аудит всех операций через систему событий

#### 5. Отсутствие процесса согласования контента
**Проблема:** Нет структурированного процесса проверки и одобрения медиа-контента перед публикацией.

**Решение:**
- Workflow система с состояниями документов (draft → pending_review → in_revision → approved → published)
- Автоматические переходы между состояниями через transitions
- Отслеживание времени согласования и метрики First-Time-Right Approval Rate
- Целевой KPI: ≥78% одобрений без переправок

#### 6. Неконтролируемое распространение контента
**Проблема:** Сложно контролировать, кто и как использует медиа-активы, нет отслеживания использования.

**Решение:**
- Система публикаций (Publications) с контролем доступа
- Защищенные ссылки для распространения (Share Links) с паролями, лимитами скачиваний и сроками действия
- Генерация рендишенов (renditions) для разных получателей и форматов
- Трекинг просмотров и скачиваний через AccessLog

#### 7. Отсутствие аналитики использования активов
**Проблема:** Невозможно понять, какие активы используются чаще, какой ROI от контента, где узкие места в процессах.

**Решение:**
- Комплексная аналитика через модуль `analytics`:
  - Asset Bank Dashboard: метрики медиатеки, топ скачиваний, распределение активов
  - Campaign Performance: эффективность маркетинговых кампаний, ROI
  - User Activity: активность пользователей, поисковые запросы
  - Search Analytics: метрики поиска, успешность поиска
  - Distribution Analytics: использование публикаций и share links
  - Content Intelligence: переиспользование контента, тренды хранилища
- Метрики: Search-to-Find Time, Asset Reuse Rate, Campaign ROI, CDN Costs
- Real-time уведомления через WebSocket о важных событиях

#### 8. Несоответствие требованиям безопасности и compliance
**Проблема:** Отсутствие контроля доступа, аудита операций, соответствия требованиям ФЗ-152.

**Решение:**
- Система прав доступа на основе Roles → Groups → Users
- Access Control Lists (ACL) для объектов
- Детальный аудит всех операций через систему событий
- Поддержка персональных данных с флагом `contains_personal_data`
- Логирование всех операций с персональными данными

#### 9. Неэффективное переиспользование контента
**Проблема:** Создание дубликатов активов вместо переиспользования существующих, рост затрат на production.

**Решение:**
- Поиск похожих активов через AI-метаданные
- Метрики переиспользования (Asset Reuse Rate)
- Целевой KPI: рост переиспользования с 40% до 62%, сокращение production costs на 22%

#### 10. Отсутствие интеграций с внешними системами
**Проблема:** Изолированность системы, невозможность автоматизировать процессы с внешними сервисами.

**Решение:**
- REST API v4 для интеграций
- Headless API для фронтенда
- Интеграция с Яндекс.Диск для импорта
- Интеграция с S3 хранилищем (Beget)
- Webhook поддержка для событий
- Расширяемая архитектура для добавления новых интеграций

## Ключевые модули системы

### Core Modules (Базовые модули Mayan EDMS)

#### 1. Documents (`mayan/apps/documents`)
**Назначение:** Управление документами и файлами

**Функциональность:**
- Загрузка, хранение и версионирование документов
- Управление типами документов (DocumentType)
- Преобразования файлов (transformations) для превью
- Полнотекстовый поиск документов
- Массовые операции (bulk operations)

**Permissions:**
- `documents.document_view` - Просмотр документов
- `documents.document_create` - Создание документов
- `documents.document_edit` - Редактирование документов
- `documents.document_trash` - Удаление документов
- `documents.document_file_download` - Скачивание файлов
- `documents.document_file_view` - Просмотр файлов

#### 2. Document States (`mayan/apps/document_states`)
**Назначение:** Workflow система и управление состояниями документов

**Функциональность:**
- Определение workflow с состояниями (Workflow, WorkflowState)
- Переходы между состояниями (WorkflowTransition)
- Экземпляры workflow для документов (WorkflowInstance)
- Автоматические действия при смене состояний (WorkflowAction)
- Отслеживание прогресса согласования

**Использование:**
- Процесс согласования активов (draft → pending_review → approved → published)
- Автоматизация бизнес-процессов
- Контроль жизненного цикла документов

#### 3. Permissions & ACLs (`mayan/apps/permissions`, `mayan/apps/acls`)
**Назначение:** Система прав доступа и контроля доступа

**Функциональность:**
- Роли (Roles) как единицы прав
- Группы (Groups) как организационные единицы
- Пользователи (Users) принадлежат группам
- Permissions назначаются ролям
- Access Control Lists для объектов

**Архитектура:**
```
Users → Groups → Roles ← Permissions
```

**Стандартные роли (из frontend):**
- **Viewer** - Только просмотр
- **Editor** - Просмотр и редактирование
- **Admin** - Полный доступ
- **Custom** - Кастомные роли

## Роли пользователей и система прав доступа

### Архитектура системы прав

Система использует трехуровневую модель прав доступа:

1. **Permissions (Права)** - Гранулярные права на действия
2. **Roles (Роли)** - Контейнеры прав, назначаются группам
3. **Groups (Группы)** - Организационные единицы, содержат пользователей
4. **Users (Пользователи)** - Принадлежат группам

**Схема:**
```
User → Group → Role ← Permissions
```

## Как должна работать система

### Пользовательские сценарии

#### Сценарий 1: Загрузка и AI-обогащение актива
1. Пользователь (Editor) загружает изображение через UI
2. Система автоматически создает Document и DocumentFile
3. Запускается Celery task для AI-анализа через провайдер (GigaChat/YandexGPT)
4. AI извлекает метаданные: описание, теги, категории, цвета, люди, локации
5. Результаты сохраняются в DocumentAIAnalysis
6. Документ автоматически переходит в состояние "draft" workflow
7. Пользователь видит обогащенные метаданные в интерфейсе

#### Сценарий 2: Поиск активов
1. Пользователь вводит поисковый запрос (например, "летний пейзаж")
2. Система ищет по:
   - AI описаниям (через GIN индексы)
   - Тегам
   - Метаданным
   - Названиям файлов
3. Результаты фильтруются по правам доступа пользователя
4. Поисковый запрос логируется в SearchQuery для аналитики
5. Пользователь находит нужный актив за 5 минут вместо 30

#### Сценарий 3: Workflow согласования
1. Контент-менеджер (Editor) загружает актив и отправляет на согласование
2. Документ переходит в состояние "pending_review"
3. Ответственный (Approver) получает уведомление
4. Approver просматривает актив и либо одобряет, либо возвращает на доработку
5. При одобрении актив переходит в "approved", затем может быть опубликован
6. Все переходы логируются в ApprovalWorkflowEvent для аналитики
7. Система отслеживает First-Time-Right метрику

#### Сценарий 4: Распространение контента
1. Маркетолог создает Publication с набором активов
2. Выбирает Recipient List (внутренние пользователи и внешние email)
3. Настраивает Rendition Presets для разных форматов и размеров
4. Система генерирует рендишены через Celery tasks
5. Создаются Share Links с паролями и лимитами
6. Ссылки отправляются получателям
7. Все просмотры и скачивания логируются в AccessLog
8. Аналитика показывает эффективность распространения

#### Сценарий 5: Аналитика использования
1. DAM менеджер открывает Asset Bank Dashboard
2. Видит метрики:
   - Топ скачиваемых активов
   - Распределение по типам файлов
   - Тренды использования
   - Метрики переиспользования
3. Переходит в Campaign Performance для анализа ROI кампаний
4. Проверяет Search Analytics для оптимизации поиска
5. Получает алерты о проблемах (низкий reuse rate, высокие CDN costs)

### Целевые метрики (KPIs)

### Стратегический план «Доработка 2026» (соответствие мировым DAM)

**Документ:** `docs/transformation-2025/Доработка_2026.md`

**Цель:** Привести Prime-EDMS в соответствие с ожиданиями мировых DAM-систем: закрыть gaps по поиску и обнаружению, продуктивности и UX, контенту (дедупликация, рендишены, водяные знаки), совместной работе (коллекции, комментарии, сравнение версий), безопасности и compliance, операциям (мониторинг, лимиты, очереди). Крупные направления (семантический поиск, видео, ingest pipeline, lifecycle, n8n, a11y) — по приоритету продукта.

**Планирование:** Спринты сгруппированы по связанным системам; для каждой функции заданы продуктовое описание, критерии приёмки и чек-лист готовности. Фазы: A (быстрые победы: поиск, UX) → B (контент, коллаборация) → C (безопасность, операции) → D (крупные инициативы по выбору). После каждого спринта — обновление Memory Bank и отчёт в docs/transformation-2025. Все новые tenant-scoped сущности следуют паттернам TenantAwareMixin и изоляции по организации.
