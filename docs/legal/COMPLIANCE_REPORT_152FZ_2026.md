## CHECKPOINT 1: Блокировка до согласия (Prior Consent)

**Требование:** Необязательные cookie (аналитика, маркетинг) не должны устанавливаться до явного согласия пользователя («Принять»).

**Проверено:**
- В проекте **нет** плагина `yandex-metrika.client.ts`. Подключение Яндекс.Метрики выполняется **только** в `public-frontend/components/CookieConsentModal.vue`.
- Функция `enableAnalytics()` вызывается **исключительно** при клике «Принять все» (`acceptAll()`). Скрипт Метрики создаётся и добавляется в `document.head` только в этот момент.
- Плагин `public-frontend/plugins/analytics.client.ts` использует **Google Analytics** (`gaId`); в `nuxt.config.ts` задан только `ymId`, `gaId` не задаётся, плагин завершается с «No GA ID configured» и не загружает никакой трекинг до согласия.

**Вывод:** ✅ **COMPLIANT** — Яндекс.Метрика инициализируется только после нажатия «Принять все», до согласия трекинг не запускается.

---

## CHECKPOINT 2: Информированное согласие (баннер)

**Требование:** В баннере должно быть явно указано, что собирается, и приведена ссылка на Политику; варианты «Отказаться» / «Только обязательные» должны быть явно видны.

**Проверено (CookieConsentModal.vue):**
- Текст: «Мы используем файлы cookie для работы сайта, аналитики и улучшения сервиса… Подробнее — в **Политике конфиденциальности**.»
- Ссылка на Политику: `<NuxtLink to="/privacy">` — видимая, подчёркнутая.
- Три кнопки в одном ряду: **«Принять все»**, **«Только обязательные»**, **«Отказаться»** — без скрытия в «Настройках».

**Вывод:** ✅ **COMPLIANT** — ссылка на `/privacy` есть, все три варианта выбора доступны и видны.

---

## CHECKPOINT 3: Чекбоксы согласия в формах сбора ПД

**Требование:** В формах, собирающих персональные данные (регистрация, обратная связь), должен быть явный чекбокс «Согласен на обработку персональных данных» со ссылкой на Политику.

**Проверено:**

| Форма | Файл | Чекбокс | Ссылка на Политику | Предустановка |
|-------|------|---------|--------------------|---------------|
| Регистрация | `RegisterForm.vue` | `agree_terms` (обязателен через схему) | Да: «политикой конфиденциальности» → `/privacy`, «условиями использования» → `/terms` | `false` (не предотмечен) |
| Контакт | `ContactForm.vue` | `consent`, атрибут `required` | Да: i18n `contact.form.consent` + `consentLink` → `/privacy` | `false` |
| Вход | `LoginForm.vue` | Только «Запомнить меня» | Нет отдельного чекбокса на обработку ПД | — |

**Вывод:** ✅ **COMPLIANT** — в формах регистрации и обратной связи есть обязательный чекбокс согласия со ссылкой на Политику, без предотметки. Форма входа не собирает новые ПД для обработки сверх уже данных при регистрации; отдельный чекбокс для входа не обязателен.

## CHECKPOINT 4: Содержимое Политики (реквизиты оператора)

**Требование:** В Политике должны быть указаны наименование, адрес, ИНН оператора и цели обработки (ст. 18.1 ФЗ-152).

**Проверено (docs/legal/privacy-policy-ru.md):**
- Оператор указан: ООО «Мэддам».
- Цели обработки (раздел 2), состав данных (раздел 5), порядок согласия (п. 3.5), права субъекта (раздел 7) — описаны.
- **Раздел 9 «Сведения об операторе»:** заполнены только наименование и заголовки полей; фактические реквизиты — плейсхолдеры:
  - «Юридический адрес: [указать при публикации]»
  - «ИНН: [указать при публикации]»
  - «ОГРН: [указать при публикации]»
  - «ОКВЭД: [указать при публикации]»
  - «Телефон: [указать при публикации]»
  - «Уполномоченный адрес электронной почты для обращений по вопросам персональных данных: [указать при публикации]»

**Вывод:** ⚠️ **RISK / WARNING** — до публикации в production необходимо заменить все плейсхолдеры на реальные реквизиты ООО «Мэддам». Иначе при проверке Роскомнадзора может быть признано неисполнение требования о неограниченном доступе к сведениям об операторе (ч. 2 ст. 18.1 ФЗ-152).

**Рекомендация:** Перед выводом сайта в production обновить раздел 9 в `docs/legal/privacy-policy-ru.md` (и при необходимости в `public-frontend/public/legal/privacy-policy-ru.md`, если контент дублируется) актуальными данными.

## CHECKPOINT 5: Логирование согласия (доказательность)

**Требование:** Оператор должен иметь возможность доказать факт и момент получения согласия (для регулятора и по ст. 14 ФЗ-152).

**Проверено:**
- **Модель** `UserConsentLog`: сохраняются `consent_type`, `ip_address`, `user_agent`, `timestamp`, `session_id`, `url_referer`. Объёма достаточно для идентификации решения пользователя и контекста (время, IP, окружение).
- **API:** `POST /api/v4/public/legal/consent/` принимает от клиента только `consent_type`, `session_id`, `url_referer`; IP и User-Agent подставляются на сервере из `request` — манипуляция с клиента минимальна.
- **Безопасность хранения IP:** IP хранится в открытом виде (не хешируется). По 152-ФЗ это допустимо при обеспечении защиты ИСПДн (режим доступа, шифрование при хранении по отраслевым стандартам). Явной криптографии полей в коде нет.

**Вывод:** ✅ **COMPLIANT** — состав лога достаточен для доказательности согласия. Рекомендуется (в рамках организационных мер): ограничить доступ к таблице `legal_userconsentlog`, обеспечить шифрование БД/томов по политике безопасности и установленные сроки хранения логов.

## Action Plan (исправления и усиления)

1. **Обязательно до production (CHECKPOINT 4):**
   - В `docs/legal/privacy-policy-ru.md` (и в `public-frontend/public/legal/privacy-policy-ru.md`, если используется копия) в разделе 9 заменить все `[указать при публикации]` на фактические реквизиты ООО «Мэддам»: юридический адрес, ИНН, ОГРН, ОКВЭД, телефон, email для обращений по ПД.

2. **Рекомендуется (CHECKPOINT 5):**
   - Оформить организационно-технические меры: ограничение доступа к `UserConsentLog`, политика хранения (срок хранения логов согласия), при необходимости — шифрование БД/дисков по требованиям к ИСПДн.

3. **По желанию (усиление доказательности):**
   - В API логирования согласия можно дополнительно сохранять версию/дату Политики (например, `policy_version` или `policy_date`), на которую дано согласие, чтобы при смене редакции Политики было видно, какую версию принял пользователь.
