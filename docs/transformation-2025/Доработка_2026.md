## 1. Цели и принципы

### 1.1 Цели дорожной карты

- Закрыть основные «дыры» Prime-EDMS по сравнению с современной DAM при минимальном риске и постепенных изменениях.
- Группировать задачи по связанным системам (поиск, UX, контент, коллаборация, безопасность, операции), чтобы вносить изменения последовательно с тестированием.
- Для каждой функции задать продуктовое описание, критерии готовности и чек-лист приёмки.

### 1.2 Принципы планирования

- **Спринты 1–2:** быстрые победы (низкий порог входа), опора на существующие данные и API.
- **Спринты 3–4:** средний объём, новые модели/ендпоинты при сохранении паттернов (TenantAwareMixin, Celery, DRF).
- **Спринты 5–6:** безопасность, compliance, операции — без ломки текущего UX.
- **Спринт 7:** крупные направления по выбору продукта; каждое может выделяться в отдельный спринт или фазу.

### 1.3 Общие требования ко всем спринтам

- Все новые tenant-scoped сущности: `TenantAwareMixin`, FK `organization`, pre_save binding при необходимости.
- API: версионирование `/api/v4/`, проверка прав, пагинация для списков.
- Тесты: unit + интеграционные для новых API и изоляции по организации.
- Документация: обновление Memory Bank (progress.md, activeContext.md) по завершении спринта.

## 3. Спринт 1 — Поиск и обнаружение

**Цель спринта:** Улучшить поиск и обнаружение активов: ориентация, «недавно просмотренные», сохранённые поиски. Всё с учётом мультитенантности.

**Связность:** Общая тема — поиск и данные, которые уже собираются (AssetEvent, документы). Минимальные новые модели.

---

### 3.1 Ориентация на бэкенде и поиск по фильтру

**Продуктовое описание:**  
Пользователь уже может выбирать фильтр «Ориентация» (portrait/landscape/square) в UI, но бэкенд не поддерживает фильтрацию по размеру изображения. Нужно: хранить или вычислять ориентацию (width/height или флаг) и поддерживать поиск/фильтрацию по ней в API документов и в оптимизированном списке.

**Ценность:** Быстрый отбор «вертикальных» или «горизонтальных» активов без ручного перебора.

**Требования:**

- **Backend:**  
  - Вариант A: при конвертации/превью сохранять `width`, `height` в метаданных файла или в расширенной модели (например, в DocumentFile или в отдельной таблице по document_file_id).  
  - Вариант B: вычисляемое поле/свойство на уровне документа (например, по первому файлу/странице).  
  - API списка документов (в т.ч. optimized): поддержка query-параметра `orientation=portrait|landscape|square`.  
  - Фильтр по организации (tenant) сохраняется.

- **Frontend:** Уже есть фильтр и URL; убедиться, что при выборе ориентации запрос уходит на бэкенд с соответствующим параметром и результаты обновляются.

**Критерии приёмки:**

- [ ] В БД или через вычисление доступна ориентация для документов с изображениями (portrait/landscape/square).
- [ ] GET `/api/v4/documents/` (и/или optimized) принимает `orientation` и возвращает только подходящие документы.
- [ ] В галерее при выборе ориентации в фильтре отображаются только соответствующие активы.
- [ ] Тесты: фильтрация по orientation, tenant isolation не нарушена.

**Чек-лист готовности функции:**

- [ ] Миграции применены (если добавлены поля).
- [ ] API документирован (docstring/OpenAPI).
- [ ] Нет регрессии поиска без фильтра ориентации.
- [ ] Progress/activeContext обновлены.

### 3.2 «Недавно просмотренные»

**Продуктовое описание:**  
В галерее (или в отдельной панели/странице) показывать список «Недавно просмотренные» активы для текущего пользователя в рамках организации. Источник данных — существующие события `AssetEvent` (event_type view/preview/download) с привязкой к пользователю и документу.

**Ценность:** Быстрый возврат к недавно открытым активам без нового поиска.

**Требования:**

- **Backend:**  
  - Endpoint, например: `GET /api/v4/headless/documents/recently-viewed/` (или в рамках analytics/headless).  
  - Параметры: `limit` (по умолчанию 20), опционально `days` (например, за последние 7 дней).  
  - Выборка: по `AssetEvent` (organization, user, event_type in (view, preview, download)), группировка по document_id, сортировка по последнему событию, возврат списка документов (id, label, thumbnail_url, …) с учётом ACL.  
  - Tenant: только текущая организация.

- **Frontend:** Блок «Недавно просмотренные» в галерее (или в сайдбаре/дашборде): вызов API, отображение карточек с переходом к документу.

**Критерии приёмки:**

- [ ] API возвращает документы, которые пользователь недавно просматривал/скачивал в данной организации.
- [ ] Список учитывает права доступа (только те документы, на которые у пользователя есть view).
- [ ] В UI блок отображается и ведёт к просмотру документа.
- [ ] Тесты: изоляция по organization, корректность выборки по пользователю.

**Чек-лист готовности функции:**

- [ ] Нет N+1 (оптимальный запрос к AssetEvent + документы).
- [ ] Пагинация или жёсткий limit (например, 50) во избежание тяжёлых выборок.
- [ ] Progress обновлён.

### 3.3 Saved Searches (сохранённые поиски)

**Продуктовое описание:**  
Пользователь может сохранить текущий поисковый запрос (строка поиска + выбранные фильтры) под именем и в дальнейшем вызывать его одной кнопкой. Опционально: уведомления «появились новые документы по сохранённому поиску» (email или in-app).

**Ценность:** Экономия времени для повторяющихся сценариев поиска; возможность подписаться на появление нового контента по критериям.

**Требования:**

- **Backend:**  
  - Модель `SavedSearch` (tenant-aware): user, organization, name, query (строка), filters (JSON: document_type, orientation, date_from, date_to, tags, …), created_at, optional notification_enabled.  
  - API: `GET/POST /api/v4/headless/saved-searches/`, `GET/PATCH/DELETE .../saved-searches/<id>/`.  
  - Выполнение сохранённого поиска: `GET .../saved-searches/<id>/run/` или передача id в endpoint списка документов (например, `?saved_search_id=<id>`) и применение сохранённых query + filters.  
  - Уведомления (опционально): периодическая задача (Celery Beat) — для сохранённых поисков с notification_enabled проверять «новые документы с момента last_notified_at», слать уведомление, обновлять last_notified_at.

- **Frontend:**  
  - В блоке поиска/фильтров: «Сохранить текущий поиск», «Мои сохранённые поиски» (список), «Выполнить» и «Удалить».  
  - При выборе сохранённого поиска подставляются query и фильтры и выполняется запрос к API документов.

**Критерии приёмки:**

- [ ] Пользователь может сохранить поиск с именем и восстановить его; список сохранённых поисков ограничен организацией и пользователем.
- [ ] Выполнение сохранённого поиска возвращает тот же набор документов, что и ручной ввод тех же параметров.
- [ ] Опционально: включение уведомлений и доставка (email или in-app) по появлению новых документов.
- [ ] Тесты: CRUD, изоляция по tenant, выполнение поиска.

**Чек-лист готовности функции:**

- [ ] Лимит количества сохранённых поисков на пользователя (например, 20) — опционально, но желательно.
- [ ] Progress/activeContext обновлены.

## 4. Спринт 2 — Продуктивность и UX

**Цель спринта:** Улучшить ежедневную продуктивность: избранное (проверка и доработка tenant isolation + UI), клавиатурные сокращения в галерее и превью.

**Связность:** Минимум новых бэкенд-моделей; фокус на API избранного и фронтенде.

---

### 4.1 Избранное: проверка и доработка (API + UI + tenant isolation)

**Продуктовое описание:**  
Избранное уже есть в Mayan: модель `FavoriteDocument`, Headless API `GET/POST .../headless/favorites/`, `.../favorites/<document_id>/`. Нужно: (1) обеспечить tenant isolation — показывать и добавлять в избранное только документы текущей организации; (2) довести UI в галерее (кнопка «В избранное»/«Из избранного», раздел «Избранное» в навигации или фильтре).

**Ценность:** Пользователь видит только «свои» избранные в контексте организации и может быстро перейти к ним из галереи.

**Требования:**

- **Backend:**  
  - При выдаче списка избранного фильтровать документы по `request.organization` (document.organization_id = current_org).  
  - При добавлении в избранное проверять, что документ принадлежит текущей организации (и что у пользователя есть право view).  
  - Если `FavoriteDocument` глобальный (без organization), фильтрация только на уровне запроса к Document по organization; отдельная модель не обязательно менять.

- **Frontend:**  
  - В карточке актива (AssetCard) или в контекстном меню: иконка/кнопка «В избранное» / «Удалить из избранного» с вызовом POST headless/favorites/<id>/ (toggle).  
  - Раздел «Избранное»: страница или фильтр «Показать только избранные», вызывающий GET headless/favorites/ и отображение результатов в той же галерее.

**Критерии приёмки:**

- [ ] Список избранного содержит только документы текущей организации.
- [ ] Добавить в избранное можно только документ текущей организации; иначе 403/404.
- [ ] В галерее есть кнопка/иконка избранного и раздел «Избранное»; состояние синхронизируется с API.
- [ ] Тесты: изоляция по organization для list и toggle.

**Чек-лист готовности функции:**

- [ ] Документация API (если менялись контракты) обновлена.
- [ ] Progress обновлён.

### 4.2 Клавиатурные сокращения (хоткеи) в галерее и превью

**Продуктовое описание:**  
Пользователь может управлять галереей и просмотром превью с клавиатуры: навигация по карточкам (стрелки, J/K), открытие превью (Enter/Space), выделение (Shift+клик уже есть), закрытие превью (Escape), возможно смена фильтра/сортировки. Список хоткеев отображается в UI (например, «?» или иконка подсказки).

**Ценность:** Ускорение работы для power users и улучшение доступности (клавиатурная навигация).

**Требования:**

- **Frontend:**  
  - Глобальные или контекстные (когда фокус в галерее/превью) обработчики keydown: стрелки вверх/вниз/влево/вправо или J/K — переход к следующему/предыдущему элементу и фокус на карточке; Enter или Space — открыть превью/детали; Escape — закрыть модал превью.  
  - Документированный список в модале «Горячие клавиши» (доступ по «?» или из меню).

- **Backend:** Не требуется (при необходимости можно логировать использование хоткеев в аналитике — опционально).

**Критерии приёмки:**

- [ ] В галерее работают как минимум: навигация стрелками (или J/K), Enter/Space — открыть превью, Escape — закрыть.
- [ ] Список горячих клавиш доступен в UI и актуален.
- [ ] Фокус и порядок навигации предсказуемы (логический порядок карточек).

**Чек-лист готовности функции:**

- [ ] Нет конфликтов с системными/браузерными сочетаниями (при необходимости использовать только в контексте галереи).
- [ ] Кратко отражено в документации (например, FEATURE-PARITY или UI_UX).

## 5. Спринт 3 — Контент: дедупликация и рендишены

**Цель спринта:** Снизить дублирование контента и упростить выдачу под каналы: дедупликация по хешу, пресеты рендишенов под каналы, водяные знаки на превью/экспорт.

**Связность:** Общая тема — контент и производные (файлы, рендишены); возможна связь с существующим модулем distribution и converter.

---

### 5.1 Дедупликация по хешу + UI «возможные дубликаты»

**Продуктовое описание:**  
При загрузке (или фоновой задачей) вычислять хеш файла (SHA-256) и сохранять его. Пользователь может видеть «возможные дубликаты» для документа (другие документы с тем же хешем в рамках организации) и при необходимости объединять или помечать дубликаты.

**Ценность:** Сокращение дублирования хранилища и путаницы из-за копий одного и того же актива.

**Требования:**

- **Backend:**  
  - Хранение хеша: поле `file_hash` (или аналог) на уровне DocumentFile или отдельная таблица FileChecksum (document_file_id, algorithm, hash). Вычисление при создании файла (сигнал или задача Celery).  
  - API: `GET /api/v4/documents/<id>/potential-duplicates/` — документы той же организации с тем же хешем (исключая текущий), с учётом ACL.  
  - Опционально: отчёт «все дубликаты в организации» (списки групп по хешу) — отдельный endpoint или раздел аналитики.

- **Frontend:**  
  - В карточке/детали документа блок «Возможные дубликаты»: список с превью и ссылками; при отсутствии дубликатов — сообщение «Дубликатов не найдено».

**Критерии приёмки:**

- [ ] Хеш вычисляется и сохраняется для новых файлов (и при желании для существующих — миграция/задача).
- [ ] Endpoint дубликатов возвращает только документы текущей организации и только с правом view у пользователя.
- [ ] В UI блок «Возможные дубликаты» отображается и ведёт к просмотру документа.
- [ ] Тесты: изоляция по tenant, корректность совпадения по хешу.

**Чек-лист готовности функции:**

- [ ] Производительность: индексы по хешу, ограничение количества возвращаемых дубликатов (например, 20).
- [ ] Progress обновлён.

---

### 5.2 Пресеты рендишенов под каналы (соцсети, печать)

**Продуктовое описание:**  
Администратор может создавать пресеты экспорта под каналы: «Instagram 1080x1080», «Печать 300 dpi A4», «VK 1200» и т.п. (размер, соотношение сторон, DPI, формат). При создании Share Link или публикации пользователь выбирает пресет, и система генерирует рендишен по этому пресету (или отдаёт уже сгенерированный).

**Ценность:** Единообразная выдача контента под каналы без ручного ресайза.

**Требования:**

- **Backend:**  
  - Модель (или расширение существующих Rendition/RenditionPreset): пресет с именем, канал (например, instagram, vk, print_a4), параметры (width, height, crop_mode, dpi, format). Tenant-aware, если рендишены различаются по организациям.  
  - API пресетов: CRUD для админов организации.  
  - Генерация рендишена по пресету: вызов существующего конвертера/пайплайна с нужными параметрами, сохранение результата и привязка к документу/публикации.  
  - Интеграция с Share Link / Publication: выбор пресета при создании ссылки или при скачивании.

- **Frontend:**  
  - В мастере создания Share Link или в настройках публикации: выбор пресета из списка (с превью размеров).  
  - При скачивании по ссылке — отдача файла в формате выбранного пресета.

**Критерии приёмки:**

- [ ] Не менее 3 предзаполненных пресетов (например, Instagram 1:1, VK, Печать A4) или настраиваемые админом.
- [ ] Рендишен по пресету генерируется (синхронно или через очередь) и отдаётся получателю.
- [ ] Список пресетов ограничен организацией (tenant).
- [ ] Тесты: создание пресета, генерация рендишена, изоляция по tenant.

**Чек-лист готовности функции:**

- [ ] Документация по форматам пресетов (и лимитам размеров) для админов.
- [ ] Progress обновлён.

### 5.3 Водяные знаки на превью/экспорт

**Продуктовое описание:**

### 6.1 Коллекции/альбомы (временные подборки с шарингом)

**Продуктовое описание:**  
Пользователь может создавать «Коллекции» (альбомы) — именованные подборки документов. Коллекция имеет владельца, опционально срок действия и список приглашённых (шаринг с другими пользователями организации). Участники могут просматривать и добавлять документы (в зависимости от прав).

**Ценность:** Совместная работа над подборками без копирования файлов; быстрый доступ к «проектным» наборам активов.

**Требования:**

- **Backend:**  
  - Модель `Collection` (tenant-aware): organization, owner (user), name, description, created_at, expires_at (optional).  
  - Модель `CollectionMember` (или m2m): collection, user, role (viewer/contributor).  
  - Связь коллекция–документы: m2m через `CollectionItem` (collection, document, added_at, added_by) с учётом того, что документы уже tenant-scoped.  
  - API: CRUD коллекций, добавление/удаление документов, управление участниками, список «мои коллекции» и «доступные мне».  
  - Права: только документы текущей организации; при добавлении в коллекцию проверять ACL на document.

- **Frontend:**  
  - Раздел «Коллекции»: список коллекций, создание, редактирование, добавление документов из галереи (выбор документов → «Добавить в коллекцию»).  
  - Просмотр коллекции: список документов в виде галереи, возможность скачать/открыть.  
  - Шаринг: приглашение пользователей организации (email или выбор из списка) с ролью viewer/contributor.

**Критерии приёмки:**

- [ ] Пользователь может создавать коллекцию, добавлять в неё документы (только из своей организации) и приглашать коллег.
- [ ] Приглашённые видят коллекцию и документы (с учётом своих ACL на документы).
- [ ] Список коллекций и документов в коллекции изолированы по организации.
- [ ] Тесты: CRUD, изоляция по tenant, права участников.

**Чек-лист готовности функции:**

- [ ] Лимит количества коллекций на пользователя/организацию (опционально).

## 7. Спринт 5 — Безопасность и compliance

**Цель спринта:** Усилить контроль доступа и соответствие требованиям: field-level права на метаданные, явный процесс «right to be forgotten» (удаление ПД по запросу).

### 7.1 Field-level права (скрытие полей метаданных по роли)

**Продуктовое описание:**  
Для части метаданных (например, «Стоимость», «Правообладатель») администратор может задать «видимость по роли»: поле отображается только пользователям с определённой ролью. В API и в UI такие поля скрыты или возвращаются пустыми для пользователей без права.

**Ценность:** Соответствие требованиям конфиденциальности и разграничение доступа к чувствительным полям без создания лишних копий документов.

**Требования:**

- **Backend:**  
  - Расширение модели типов метаданных (MetadataType) или отдельная конфигурация: список полей (или типов метаданных) с привязкой «какие роли могут видеть».  
  - При сериализации документа и при отдаче метаданных: фильтровать поля по ролям текущего пользователя.  
  - В поиске: не индексировать чувствительные поля для пользователей без права или не возвращать их в результатах (в зависимости от политики).

- **Frontend:** Не отображать скрытые поля в формах и в карточке документа.

**Критерии приёмки:**

- [ ] Администратор может назначить для типов метаданных (или полей) ограничение видимости по ролям.
- [ ] Пользователь без роли не видит значение поля в API и в UI.
- [ ] Поиск не раскрывает чувствительные данные пользователям без права.
- [ ] Тесты: проверка фильтрации по ролям, изоляция по tenant сохранена.

**Чек-лист готовности функции:**

- [ ] Документация для админов (как настроить field-level права).
- [ ] Progress обновлён.

### 7.2 Процесс «Right to be forgotten» (удаление ПД по запросу)

**Продуктовое описание:**  
Субъект персональных данных (или уполномоченное лицо) может подать запрос на удаление своих ПД. Система поддерживает учёт таких запросов, поиск и удаление/анонимизацию данных (документы, метаданные, логи, комментарии с ПД), а также аудит выполнения запроса.

**Ценность:** Соответствие ФЗ-152 и GDPR-like сценариям; снижение рисков при проверках.

**Требования:**

- **Backend:**  
  - Модель `PersonalDataErasureRequest` (или аналог): заявитель, контакт, описание, статус (pending/approved/completed/rejected), created_at, completed_at, исполнитель.  
  - Процесс: заявка создаётся (вручную админом или через форму); после одобрения — задача (Celery или ручной скрипт) ищет все записи, связанные с субъектом (по email, ФИО, user_id и т.д.), в документах, метаданных, логах, комментариях, и выполняет удаление или анонимизацию.  
  - Аудит: кто, когда и какие записи обработал — запись в отдельный лог или таблицу.  
  - Документация: описание процесса для оператора (как принять заявку, как запустить удаление, как зафиксировать результат).

- **Frontend:** Опционально: форма заявки (публичная или в админке), статус заявки для заявителя. Минимум — админ-интерфейс для создания заявки и просмотра статуса.

**Критерии приёмки:**

- [ ] Заявка на удаление ПД фиксируется и имеет статус.
- [ ] Описан и реализован процесс поиска и удаления/анонимизации данных по субъекту.
- [ ] Аудит выполнения заявки ведётся.
- [ ] Документация процесса есть (внутренняя или в docs/legal).

**Чек-лист готовности функции:**

- [ ] Согласовано с юристом/DPO (опционально, но желательно).
- [ ] Progress обновлён.

**Требования:**

**Критерии приёмки:**

### 8.2 Лимиты на размер/тип файла и приоритеты очередей

**Продуктовое описание:**

- **Frontend:** При ошибке загрузки показывать понятное сообщение (файл слишком большой / тип не разрешён).

**Критерии приёмки:**

- [ ] Загрузка файла больше лимита или неразрешённого типа отклоняется с ясной ошибкой.
- [ ] Настройки лимитов хранятся по организации (или глобально) и применяются.

## 9. Спринт 7 — Крупные направления (опционально)

### 9.1 Семантический поиск (эмбеддинги + векторный поиск)

**Объём:** Большой (модели эмбеддингов, индексация, API поиска).  
**Зависимости:** Решение по модели эмбеддингов (локальная или облачная API).

### 9.2 Видеомодуль (транскрипция, субтитры, ключевые кадры)

**Описание:** Для видео-документов: извлечение ключевых кадров, генерация субтитров (speech-to-text), транскрипция для поиска. Хранение метаданных и привязка к таймкоду.  
**Объём:** Большой (конвертер/ffmpeg, очереди, хранилище превью по времени).  
**Зависимости:** Выбор сервиса транскрипции (облачный или локальный).

### 9.3 Ingest pipeline (правила при приёме, очереди, мониторинг)

**Описание:** Настраиваемые правила при загрузке: автотегирование, назначение папки/кабинета по дате или типу, валидация форматов. Очередь приёма с мониторингом (сколько в очереди, ошибки).  
**Объём:** Средний–большой (новые модели правил, движок применения правил, UI мониторинга).  
**Зависимости:** Существующие очереди и конвертер.

---

### 9.4 Lifecycle (правила архивации и удаления по времени/статусу)

**Описание:** Правила вида «документы в статусе X старше N дней переместить в архив» или «временные файлы удалить через 90 дней». Периодические задачи (Celery Beat), аудит переносов/удалений.  
**Объём:** Средний (модель правил, движок, безопасность от случайного удаления).  
**Зависимости:** Workflow и статусы документов.

### 9.5 n8n / коннекторы (ноды для DAM, интеграции с CMS/маркетингом)

**Описание:** Готовые ноды для n8n (или аналога): загрузка в DAM, поиск, создание Share Link. Коннекторы к внешним CMS/маркетинговым платформам (1С, Bitrix, и т.д.) для синхронизации контента.  
**Объём:** Средний на ноду/коннектор; зависит от количества целевых систем.  
**Зависимости:** Стабильный REST API и webhooks.

### 9.6 Доступность (a11y): аудит и доработки под WCAG

**Описание:** Аудит интерфейса галереи и ключевых потоков на соответствие WCAG 2.1 (уровень AA): контраст, фокус, скринридеры, клавиатурная навигация. Исправление выявленных нарушений и закрепление практик в гайдлайнах.  
**Объём:** Средний (аудит + итеративные правки).  
**Зависимости:** Хоткеи (Спринт 2) и стабильная разметка компонентов.

## 10. Зависимости и порядок выполнения

- **Спринты 1 и 2** можно выполнять параллельно разными командами (поиск vs UX); оба не блокируют остальные.
- **Спринт 3** желательно после 1–2 (пользователи уже пользуются улучшенным поиском и избранным).
- **Спринт 4** логически после 1 (saved searches могут использоваться в контексте коллекций); зависимость слабая.
- **Спринты 5 и 6** независимы от 1–4; их можно ставить в любое окно.
- **Спринт 7** — по приоритету продукта; a11y (9.6) разумно после Спринта 2 (хоткеи уже есть).

Рекомендуемый порядок по фазам:

1. **Фаза A (быстрые победы):** Спринт 1 → Спринт 2.  
2. **Фаза B (контент и коллаборация):** Спринт 3 → Спринт 4.  
3. **Фаза C (безопасность и операции):** Спринт 5 → Спринт 6.  
4. **Фаза D (по выбору):** Отдельные инициативы из Спринта 7.

После каждого спринта: прогон регрессионных тестов, обновление Memory Bank (progress.md, activeContext.md), краткий отчёт в `docs/transformation-2025/` (например, `SPRINT_DORABOTKA_2026_1.md`).
